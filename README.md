# CCSDS Space Data Link Security as Code

**Turning the CCSDS space-link security standards into automated, tested, traceable guardrails.**

A spacecraft and its ground station only talk securely if both ends load the same
*Security Association (SA) database*: which virtual channels are protected, with
which algorithm, key length, MAC size, and anti-replay window. Today that
database is usually checked by a human reading a spreadsheet against a PDF.

This repo replaces that review with code. It reads an SA database as YAML and
checks it against **24 policies** written in [Rego](https://www.openpolicyagent.org/docs/latest/policy-language/)
(Open Policy Agent), each one traced to a specific clause of:

| Standard | What it governs | Policies |
|---|---|---|
| **CCSDS 355.0-B-2** Space Data Link Security (SDLS) Protocol | SA structure, SPI rules, channel binding, anti-replay, Security Header/Trailer format | `SDLS-001` … `SDLS-032` |
| **CCSDS 352.0-B-2** CCSDS Cryptographic Algorithms | AES, key sizes, CTR/GCM modes, GCM tag length, HMAC/CMAC choices | `CRYPTO-001` … `CRYPTO-006` |
| **Mission profile** (rationale from CCSDS 350.1-G threat analysis) | Decisions CCSDS leaves to the mission: authenticated uplink, key handling | `MISSION-001`, `MISSION-002` |

The full control → policy → test matrix is in [`docs/traceability.md`](docs/traceability.md).
It is **generated from the policy code**, and CI fails if it goes stale.

```text
$ make scan FILE=examples/non-compliant/legacy-cubesat.sdls.yaml
FAIL - [MISSION-001] VC tc-commands: telecommand channel TC:0/77/0 has no SA providing
       authentication or authenticated encryption (mission profile, CCSDS 355.0-B-2 authentication service)
FAIL - [SDLS-021] SA spi=5 (Housekeeping telemetry): sequence number window must be a
       positive integer, got 0 (CCSDS 355.0-B-2 §4.2.2.6.1, Table 6-1)
FAIL - [CRYPTO-005] SA spi=5 (Housekeeping telemetry): SHA-1 shall not be used (CCSDS 352.0-B-2 §4.2.2.3.2)
FAIL - [CRYPTO-002] SA spi=0 (Telecommand uplink): new implementations shall use a 256-bit AES key,
       got 128 (CCSDS 352.0-B-2 §3.2, §4.3.1)
WARN - [CRYPTO-003] SA spi=0 (Telecommand uplink): CCSDS implementations use Counter Mode;
       CBC needs a documented justification (CCSDS 352.0-B-2 §3.3)
...
```

Every finding says **what** is wrong, **where** (SA or VC), and **which clause** requires it.
An auditor can follow the trail; an engineer can fix it without opening the standard.

## Why this project exists

I come from Governance, Risk and Compliance. In GRC the usual deliverable is
"control X is implemented, here is the evidence," collected by hand once a year.
This project shows the other half of that job: taking a control written in
standards language, deciding what it means for a concrete configuration, and
enforcing it on every change, with tests that prove the enforcement works.

What it demonstrates:

- **Reading a standard like an engineer.** Each `shall` in SDLS and the CCSDS
  algorithms book became a testable predicate over real configuration fields.
  Where the standard allows a choice that the two ends must agree on a priori
  (SHA-384 instead of SHA-256, truncated HMAC tags), the policy requires that
  agreement to be recorded in the SA, instead of guessing.
- **Separating the standard from the mission's risk decisions.** CCSDS defines
  mechanisms; it does not say that a mission *must* authenticate its uplink.
  `MISSION-*` rules make that decision explicit and tunable
  ([`policy/mission/profile.rego`](policy/mission/profile.rego)), so nobody
  mistakes a mission choice for a CCSDS requirement.
- **Graded enforcement.** "Shall" becomes `deny` (blocks the pipeline). "Should"
  or "permitted but consider carefully" becomes `warn` (visible, justified,
  not blocking). See `CRYPTO-003` (non-CTR modes) and `SDLS-022` (wide TC window).
- **Fail-closed policy design.** A missing field must never make a check pass.
  Writing the tests exposed exactly that bug (see
  [`docs/design.md`](docs/design.md#lesson-learned-fail-closed)): the fix and a
  regression test for each case are in the repo.
- **Evidence as a by-product.** The traceability matrix, test counts and
  coverage are generated by the pipeline, not maintained in a spreadsheet.

## How it works

```text
           mission.sdls.yaml  (SA database: VCs, SAs, algorithms, key refs)
                    │
                    ▼
   ┌──────────────────────────────────────────┐
   │ Conftest / OPA                            │
   │  policy/sdls/      ← CCSDS 355.0-B-2      │
   │  policy/crypto/    ← CCSDS 352.0-B-2      │
   │  policy/mission/   ← mission profile      │
   └──────────────────────────────────────────┘
                    │ deny → pipeline fails     warn → reported
                    ▼
   findings with policy ID + CCSDS clause (text or JSON for SIEM/GRC tooling)
```

The input format is described in [`docs/input-format.md`](docs/input-format.md)
and illustrated by three example databases:

| Example | Purpose |
|---|---|
| [`examples/compliant/demosat-1.sdls.yaml`](examples/compliant/demosat-1.sdls.yaml) | A well-formed mission: AES-GCM-256 uplink, HMAC-SHA-256 housekeeping, AES-CTR payload, untouched idle VC. Passes all 24 policies. |
| [`examples/non-compliant/legacy-cubesat.sdls.yaml`](examples/non-compliant/legacy-cubesat.sdls.yaml) | SDLS bolted onto an old design: encryption-only uplink, SHA-1, inline key, SPI 0, SA on an idle VC. |
| [`examples/non-compliant/gcm-misconfig.sdls.yaml`](examples/non-compliant/gcm-misconfig.sdls.yaml) | Looks correct at a glance (AES-GCM-256) but has a 64-bit tag, duplicate SPI, overlapping SAs and a 1024-frame replay window. |

## Quality gates

| Gate | Command | What it proves |
|---|---|---|
| Lint | `make lint` | `opa fmt` clean, strict compile |
| Unit tests | `make coverage` | 55 tests, **100 % line coverage** enforced |
| End-to-end | `make examples` | Compliant file is clean; each bad file yields **exactly** the expected policy IDs (no misses, no false positives) |
| Traceability | `make traceability-check` | Matrix matches the code; every policy has at least one test |

All four run in GitHub Actions on every push ([`.github/workflows/policy-ci.yml`](.github/workflows/policy-ci.yml)).

## Quick start

```bash
# Requires OPA >= 1.0 and Conftest >= 0.56
make all                                    # what CI runs
make scan FILE=examples/compliant/demosat-1.sdls.yaml
conftest test my-mission.sdls.yaml -p policy --all-namespaces -o json   # machine-readable
```

## Repository layout

```text
policy/
  lib/sdls.rego              shared helpers, finding format
  sdls/                      CCSDS 355.0-B-2 (structure, channel binding, anti-replay, frame format)
  crypto/algorithms.rego     CCSDS 352.0-B-2
  mission/                   mission profile (tunable values + protection rules)
tests/                       Rego unit tests and fixtures
examples/                    compliant and non-compliant SA databases (+ expected findings)
scripts/                     traceability generator, end-to-end verifier
docs/                        design decisions, input format, sources and caveats
```

## Scope and honesty notes

- Clause numbers were taken from the public CCSDS Blue Book for 352.0-B-2 and from
  the public review draft of the SDLS revision (355.0-P-1.1) for 355.0-B-2. See
  [`docs/sources.md`](docs/sources.md) for exactly what was checked and what to
  re-verify against the published issue.
- This checks **configuration**, not implementations. It cannot tell whether a
  crypto unit actually rejects replayed frames, only whether it was told to.
- All missions, IDs and key references are fictional. No key material appears anywhere.

## Roadmap

- **SDLS Extended Procedures (CCSDS 355.1-B-1):** key and SA lifecycle states, OTAR, so that a
  key referenced by an operational SA cannot be in a deactivated state.
- **Ground segment IaC:** the same policies applied to the SA database as it is
  deployed (Kubernetes ConfigMap / Terraform for the KMS that holds the keys).
- **Import from real tools:** adapter from NASA CryptoLib's SA configuration to this input format.
- **OSCAL output:** emit findings as OSCAL assessment results so the evidence lands directly in a GRC tool.
