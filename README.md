# CCSDS Space Data Link Security as Code

**Checking the CCSDS space link security rules automatically, with tests and a clear link back to the standard.**

A spacecraft and its ground station can only talk securely if both sides load
the same *Security Association (SA) database*: which virtual channels are
protected, with which algorithm, key length, MAC size and anti-replay window.
Today a person usually checks that database by reading a spreadsheet next to a PDF.

This repo does that review with code. It reads an SA database in YAML and
checks it against **24 policies** written in [Rego](https://www.openpolicyagent.org/docs/latest/policy-language/)
(Open Policy Agent). Each policy points to a clause of one of these:

| Standard | What it covers | Policies |
|---|---|---|
| **CCSDS 355.0-B-2** Space Data Link Security (SDLS) Protocol | SA structure, SPI rules, channel binding, anti-replay, Security Header/Trailer format | `SDLS-001` … `SDLS-032` |
| **CCSDS 352.0-B-2** CCSDS Cryptographic Algorithms | AES, key sizes, CTR/GCM modes, GCM tag length, HMAC/CMAC choices | `CRYPTO-001` … `CRYPTO-006` |
| **Mission profile** (reasons taken from the CCSDS 350.1-G threat analysis) | Decisions that CCSDS leaves to the mission: authenticated uplink, key handling | `MISSION-001`, `MISSION-002` |

The full control → policy → test matrix is in [`docs/traceability.md`](docs/traceability.md).
A script **generates it from the policy code**, and CI fails if it is out of date.

```text
$ make scan FILE=examples/non-compliant/legacy-cubesat.sdls.yaml
FAIL - [MISSION-001] VC tc-commands: telecommand channel TC:0/77/0 has no SA providing
       authentication or authenticated encryption (mission profile, CCSDS 355.0-B-2 authentication service)
FAIL - [SDLS-021] SA spi=5 (Housekeeping telemetry): sequence number window must be a
       positive integer, got 0 (CCSDS 355.0-B-2 §4.2.2.6.1, Table 6-1)
FAIL - [CRYPTO-005] SA spi=5 (Housekeeping telemetry): SHA-1 shall not be used (CCSDS 352.0-B-2 §4.2.2.3.2)
FAIL - [CRYPTO-002] SA spi=0 (Telecommand uplink): new implementations shall use a 256-bit AES key,
       got 128 (CCSDS 352.0-B-2 §3.2, §4.3.1)
WARN - [CRYPTO-003] SA spi=0 (Telecommand uplink): CCSDS implementations use Counter Mode;
       CBC needs a documented justification (CCSDS 352.0-B-2 §3.3)
...
```

Each finding says **what** is wrong, **where** (SA or VC) and **which clause** asks for it.
An auditor can follow it, and an engineer can fix it without opening the standard.

## Why I made this

My background is Governance, Risk and Compliance. In GRC the normal output is
"control X is implemented, here is the evidence", collected by hand once a year.
With this project I wanted to do the other part of the job: take a control
written in the language of a standard, decide what it means for a real
configuration, and check it on every change, with tests that show the check works.

What it shows:

- **Turning a standard into checks.** I turned each `shall` in SDLS and in the
  CCSDS algorithms book into a test on real configuration fields. When the
  standard allows a choice that both sides must agree on before (SHA-384
  instead of SHA-256, truncated HMAC tags), the policy asks for that agreement
  to be written in the SA, instead of guessing.
- **Keeping the standard apart from mission risk decisions.** CCSDS defines
  mechanisms. It does not say that a mission *must* authenticate its uplink.
  The `MISSION-*` rules make that decision visible and configurable
  ([`policy/mission/profile.rego`](policy/mission/profile.rego)), so nobody
  confuses a mission choice with a CCSDS requirement.
- **Two levels of enforcement.** "Shall" becomes `deny` (it stops the pipeline).
  "Should", or "allowed but think about it", becomes `warn` (visible but not
  blocking). See `CRYPTO-003` (non-CTR modes) and `SDLS-022` (wide TC window).
- **Fail closed.** A missing field must never make a check pass. Writing the
  tests showed me exactly this bug (see
  [`docs/design.md`](docs/design.md#lesson-learned-fail-closed)). The fix and a
  regression test for each case are in the repo.
- **Evidence comes from the pipeline.** The traceability matrix, the test count
  and the coverage are generated by CI, not kept in a spreadsheet.

## How it works

```text
           mission.sdls.yaml  (SA database: VCs, SAs, algorithms, key refs)
                    │
                    ▼
   ┌──────────────────────────────────────────┐
   │ Conftest / OPA                            │
   │  policy/sdls/      ← CCSDS 355.0-B-2      │
   │  policy/crypto/    ← CCSDS 352.0-B-2      │
   │  policy/mission/   ← mission profile      │
   └──────────────────────────────────────────┘
                    │ deny → pipeline fails     warn → reported
                    ▼
   findings with policy ID + CCSDS clause (text, or JSON for SIEM/GRC tools)
```

The input format is in [`docs/input-format.md`](docs/input-format.md), and there
are three example databases:

| Example | What it is for |
|---|---|
| [`examples/compliant/demosat-1.sdls.yaml`](examples/compliant/demosat-1.sdls.yaml) | A good mission: AES-GCM-256 uplink, HMAC-SHA-256 housekeeping, AES-CTR payload, idle VC left alone. Passes all 24 policies. |
| [`examples/non-compliant/legacy-cubesat.sdls.yaml`](examples/non-compliant/legacy-cubesat.sdls.yaml) | SDLS added on top of an old design: encryption-only uplink, SHA-1, key written inline, SPI 0, SA on an idle VC. |
| [`examples/non-compliant/gcm-misconfig.sdls.yaml`](examples/non-compliant/gcm-misconfig.sdls.yaml) | Looks fine at first (AES-GCM-256) but has a 64 bit tag, a duplicate SPI, overlapping SAs and a 1024 frame replay window. |

## Quality gates

| Gate | Command | What it shows |
|---|---|---|
| Lint | `make lint` | `opa fmt` clean, strict compile |
| Unit tests | `make coverage` | 55 tests, **100 % line coverage** required |
| End to end | `make examples` | The good file is clean; each bad file gives **exactly** the expected policy IDs (nothing missing, no false positives) |
| Traceability | `make traceability-check` | The matrix matches the code; every policy has at least one test |

All four run in GitHub Actions on every push ([`.github/workflows/policy-ci.yml`](.github/workflows/policy-ci.yml)).

## Quick start

```bash
# Needs OPA >= 1.0 and Conftest >= 0.56
make all                                    # same as CI
make scan FILE=examples/compliant/demosat-1.sdls.yaml
conftest test my-mission.sdls.yaml -p policy --all-namespaces -o json   # JSON output
```

## Where it is used

My [ccsds-sdls-groundlink](https://github.com/jfabio-navarrom/ccsds-sdls-groundlink)
project (a secure link with an ESP32-C5 as the satellite) scans its own SA
database with these policies in CI. The findings it gets are accepted in a risk
register with an owner and a review date.

## Repository layout

```text
policy/
  lib/sdls.rego              shared helpers, finding format
  sdls/                      CCSDS 355.0-B-2 (structure, channel binding, anti-replay, frame format)
  crypto/algorithms.rego     CCSDS 352.0-B-2
  mission/                   mission profile (configurable values + protection rules)
tests/                       Rego unit tests and fixtures
examples/                    compliant and non-compliant SA databases (+ expected findings)
scripts/                     traceability generator, end to end check
docs/                        design decisions, input format, sources and limits
```

## Limits

- I took the clause numbers from the public CCSDS Blue Book for 352.0-B-2, and
  from the public review draft of the SDLS revision (355.0-P-1.1) for 355.0-B-2.
  [`docs/sources.md`](docs/sources.md) says exactly what I checked and what
  must be checked again against the published issue.
- This checks **configuration**, not implementations. It can not tell if a
  crypto unit really rejects replayed frames, only if it was configured to.
- All missions, IDs and key references are made up. There is no key material anywhere.
